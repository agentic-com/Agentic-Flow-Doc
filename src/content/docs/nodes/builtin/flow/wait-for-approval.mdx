# Wait For Approval

Pause a run and wait for a human decision before continuing.

## What it does

Pauses the run until a person approves or rejects it. The node produces no output on its own — the run parks and waits for a decision. When a decision arrives, the items that were waiting flow out of the port the decision chose: **Approved** or **Rejected**. Use this as a checkpoint before any consequential action that warrants a human sign-off.

## When to use it

- Any human-in-the-loop checkpoint before a consequential step: sending an email, making a purchase, publishing content, or triggering an external action.
- The work after **Approved** runs only on approval; **Rejected** is an ordinary branch for handling a no or fallback behavior.
- When waiting indefinitely is acceptable — the run survives browser restarts and remains in the Executions pane until approved, rejected, or manually cancelled.

## Inputs and settings

| Setting | Notes |
| --- | --- |
| Prompt | The question or text shown to the person making the decision. Appears on the paused run in the Executions pane. |

## Outputs

The node draws two output handles:

- **Approved** — Items flow here when the person approves the run.
- **Rejected** — Items flow here when the person rejects the run.

## One approval for a batch

Fed a list of items, this node pauses **once** for the whole batch — a single decision that then routes all the items to **Approved** or **Rejected** together. If you need a separate decision **per item**, put the node inside a [Loop](/nodes/builtin/flow/loop/) or [Split in Batches](/nodes/builtin/flow/splitinbatches/) body, which runs it once per item (and stays durable across restarts).

## Paused run visibility and control

A paused run appears in the **Executions** pane, where a person with access can approve, reject, or cancel it. The run waits indefinitely — it does not time out or resume on its own — and persists even if the browser restarts or the window closes. Cancelling a paused run stops it without flowing items to either output.

You're told when a run needs you: a **“waiting for you” count** in the top bar, a **sound** (a chime when the app is open, or the desktop notification's own sound when it isn't), and — when the app isn't in front of you — a **desktop notification** you can click to jump straight to the waiting run. If you're on a web page (say the run was started from the right-click menu), an **approval card is dropped right onto the page** so you can answer without opening the extension — Approve/Reject for an approval, or the fields for a form. The same applies to any pausing step that needs a response, including an [In-Page Form](/nodes/builtin/flow/) and a pause inside a [sub-workflow](/nodes/builtin/lambda/lambdaworkflow/).

## Wait For Approval vs. action approval

This node is a **durable checkpoint you design into a flow**: it pauses a whole step, waits indefinitely, and survives browser restarts. It is different from the **live action approval** that gates the model-driven action tools ([Browser Tool](/nodes/builtin/ai/aidependencies/tools/browser/), [HTTP Request Tool](/nodes/builtin/ai/aidependencies/tools/http-request/), [MCP Client Tool](/nodes/builtin/ai/aidependencies/tools/mcp-client/)) — that gate is automatic, fires on each action the model decides to take, and auto-rejects after a timeout. Use this node for deliberate human sign-off on a step; the action gate is always-on and requires no node. See [Action Approval](/advanced-ai/concepts/action-approval/).
