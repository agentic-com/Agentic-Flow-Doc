A **workflow** is a set of steps linked together. A **trigger** decides when it starts.

Each step does one thing, like:

- Get text from the page
- Click a button
- Fill a form field
- Clean or format the data
- Send the result somewhere

---

## How to build a new workflow

1. Click the AWFlow icon in your browser.
2. Click **Add Workflow** (or **+ Create › New workflow**). This opens a single wizard with three steps:
   1. **Source** — choose how you want to start: **Template** (browse a curated gallery of ready-made templates), **Blank** (start empty: **Runs on its own**, preselected, or **Reusable workflow**, called by other workflows), **Marketplace** (browse and install a community-published workflow, with its permissions shown before you install), or **Import** (load a workflow from a `.awf` file or a URL).
   2. **Choose** — pick the specific template, marketplace listing, or file/URL for the source you selected (skipped for **Blank**).
   3. **Details** — name your workflow, add an optional description, and pick where it's saved (this defaults to your storage preference; anonymous users save to **Local**).

New workflows are created **Off**, in the folder you have open. Template cards say how much setup they need ("No setup", "~10 min · Google account"); templates with no setup come first. A new **Schedule** step starts at *every day at 09:00*, an HTTP Request at *GET*, a Wait at *1 minute*.

You can also paste steps or a whole `.awf` file into any canvas: see [Export & import](/app/workflows/export-import/).
3. Click **Create**, then **Add first step…** on the canvas.
4. Search for a node you want (for example **Get Selected Text**) and add it.
5. Click the node to open its settings and choose the options you want.
6. Add more nodes and connect them.
7. To test, open the page you want to automate, then click **Execute Workflow**.
8. Click each node to see its output.

> When you open a template (or any pre-wired workflow) for the first time, the editor shows a checklist of what's missing before you can run it — such as a credential to connect or a required field to fill in. Fix each item from the checklist, then click **Run** once everything is ready.

You can automate tasks such as:

- Extracting page content
- Interacting with forms or elements
- Processing data with AI
- Branching logic or loops
- Combining browser and external data

If you’re new, try the [Quick Intro Tutorial](/get-started/first-workflow/) first to experiment with basic browser nodes.

## Run workflows manually vs automatically

### Manual execution

Best for testing, or when you want to decide exactly when to run:

1. Open the page you want to automate.
2. Open the extension and choose your workflow.
3. Press **Run**.
4. Nodes will run in order using the current page state.

> After a run finishes, the **Last run** tab of the panel on the right shows what actually happened in plain words — not raw logs. On success, you get the real-world effect of the run (for example, "Sent to #general") plus a link to verify it yourself. On failure, you get the plain-language cause, a few things to try, and the option to show technical details if you need them. See [Run from the canvas](/app/workflows/executions/run-from-the-canvas/).

### The panel on the right

One floating panel below the run buttons holds three tabs, and opens the one that matters most on its own:

- **Story** — [How this flow works](/app/workflows/narration/), step by step.
- **Ready to run** — what is still missing (a connection, a required field) with a button to fix each one. **Ready to run?** in the toolbar opens this tab; its count is the number of things left. Steps that still need setup also carry an amber dot on the canvas — hover it to see what's missing.
- **Last run** — the outcome of the last run.

**Ready to run** also holds the **Workflow doctor** (deeper checks) and, after an import, the [variables](/app/variables/) to set. See [Steps › Ready to run](/app/workflows/components/nodes/#ready-to-run).

Close it with the collapse button; it shrinks to a small pill under the run buttons.

### Field checks and previews

In a step's settings, a field is checked against what the step expects as soon as you leave it — a required field left empty or a value in the wrong format shows a short message under the field. Fields that map data from earlier steps with `{{ }}` show a preview line: the value they get at the current item, or what's wrong with the expression. See [Expressions](/concepts/data/data-mapping/data-mapping-expressions/#typing-an-expression).

### Automatic runs with triggers

If your workflow starts with a **trigger node**, it can start on its own once the workflow is **On**. Switch it **On** with the switch in the canvas header, or with **Turn on** in the workflow list.

Examples:

- [When a page loads](/nodes/builtin/trigger/pageload/) — start when a matching page loads
- [Schedule](/nodes/builtin/trigger/schedule/) — start at set times
- [Keyboard shortcut](/nodes/builtin/trigger/hotkey/) — start with a keyboard shortcut
- [From the right-click menu](/nodes/builtin/trigger/contextmenu/) — start from the right-click menu on a page
- [When something on a page changes](/nodes/builtin/trigger/elementchange/) — start when something on a page changes
- [New email, New row and the other polling triggers](/concepts/flow/polling-triggers/) — start when something new appears in an app
- [When a form is submitted](/nodes/builtin/trigger/form-trigger/) — start when someone fills in a form

[When I press Run](/nodes/builtin/trigger/whenstarted/) is the manual trigger: it runs only when you press **Run**. A workflow with only this trigger shows **Runs when you press Run** instead of the On/Off switch.

Even when you use triggers, manual runs are still useful for testing.

## Execution context and limitations

- Workflows run in the page you currently view, so they see **real-time content** and page structure.
- Because they run inside the browser, workflows are subject to **browser security rules** (e.g. cross-origin constraints).
- Very large workflows or heavy processing may hit browser performance limits (memory, CPU).
- Workflows are saved locally in your extension — they persist across browser sessions. You can export/import workflows to share or back them up.

## Saving and shortcuts

The status next to **Save** tells you where you stand: **Saved**, **Unsaved changes**, **Saving…**, or **Couldn't save · Retry**. Changes you make while a run is in progress stay unsaved until you save.

If you try to leave the canvas with unsaved changes, you're asked whether to **Save & leave**, **Leave without saving** or **Stay**.

Unsaved changes are also kept as a **draft** on this device, so closing the panel or the tab doesn't lose them: when you open the workflow again, a bar offers **Restore** or **Discard**. If the workflow was saved meanwhile in another window, the bar says so. When the same workflow is open in another window, the canvas shows **Also open in another window**. Cloud workflows are also re-checked every minute while you look at them. Two windows editing the same workflow can't overwrite each other: saving over a newer version asks you to **Reload** or **Keep mine**, and a canvas without edits reloads by itself when the workflow changes elsewhere.

| --- | --- |
| <kbd>⌘</kbd> <kbd>S</kbd> / <kbd>Ctrl</kbd> <kbd>S</kbd> | Save |
| <kbd>⌘</kbd> <kbd>Z</kbd> / <kbd>Ctrl</kbd> <kbd>Z</kbd> | Undo |

### Workflow info

**Workflow info**: click the workflow's name in the canvas header to see its status (with the same On/Off switch), its version (with **History**), its behaviour (with **Preview upgrade** on a Classic workflow), where it is stored (with **Change**), its folder (with **Move**), when it was created and last saved, and a link to **Workflow settings**.

For an **installed** workflow, the popover says *Installed* and who made it (*From the Marketplace*), and checks for an update when you open it: *v3 · v4 available* with **Update…**, *Up to date* with **Check again**, or *Can't check offline*. Only the author can change it; **Make a copy** makes it yours (*Make a copy of "Invoice chaser"?*):

## Tips for building reliable workflows

- Add nodes gradually. Test often instead of building everything at once.
- Use **If / conditional nodes** to manage different paths.
- In each node, inspect results to understand what data you have.
- Use meaningful names or notes for nodes — this helps you and others read the flow.
- Start with small exported examples or existing workflows to learn patterns and best practices.
